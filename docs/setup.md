# Setup and maintenance

## First install and existing work

1. Confirm Git, Node.js 22.16+, FFmpeg and FFprobe are on PATH. Use GitHub CLI authentication or a supported Git credential helper for a private HTTPS repository. Configure SSH and set `KAT_REPO` to the exact SSH remote if you prefer. The installer uses your Git authentication and stores no credentials.
2. Run `sh bootstrap.sh`. Set `KAT_HOME` to choose a different installation directory. Use `KAT_PORT` on the first install if a separate Studio is already running on 52830. `KAT_NO_BROWSER=1` prints the loopback URL without opening a browser. Keep the URL private.
3. The installed skill is written to `~/.agents/skills/kat-studio` or to the base directory in `KAT_SKILL_DIR`. Setup preserves an existing user skill and tells you if one is already present. The installation stores its data location and port in the installation root's `workspace.json`. The development checkout can also use `node kat.mjs` directly, with its own `KAT_HOME`.
4. Private projects travel via Studio backups. Transfer the entire backup directory privately, with its manifests and content-addressed objects. Set `KAT_BACKUP_DIR` to it and run `node kat.mjs restore <new-directory>`. To adopt the recovered database in a fresh install, set `KAT_DATA` to the absolute recovered `Studio Data` folder when running the bootstrap for the first time. For an existing portable install, stop Studio and set the `data` field in its local `workspace.json` explicitly. Retain the former data directory and backups. The recovered application files can be used to recover its private local guides and assets. GitHub tracks the app source, and workspace backup transfer is separate.
5. Run `node kat.mjs status`. The optional existing Introduction revision renderer requires Python 3, Pillow and NumPy from `requirements.txt`, Poppins Regular and Bold and Playfair Display Italic fonts in `KAT_FONT_DIR` or the install's `fonts` directory, and the restored project media. The macOS user fonts directory is also recognized. Use `KAT_PYTHON` for a virtual environment and `KAT_CODEX_HOME` if the Codex CLI uses a dedicated sign-in. These prerequisites remain local and the installer leaves package-manager decisions to you. Standard previews and FFmpeg QA work with the core prerequisites.

## Develop, review and publish

Open the development checkout on `main`. Run `node --test` before saving. Stage the specific files using `git add <paths>`, inspect `git diff --cached`, and use `node kat.mjs save --message "Describe the change"`. The CLI uses your Git identity. Never stage local project data, access tokens, personal files or credentials. Review the staged changes for workstation paths, authentication data, client media and raw workspace records. The release bundles style guidance and reusable editing lessons. Use verified backups to move project-specific memory securely.

For the first GitHub publish, use an empty authorized repository. Configure its exact URL as `origin` (and `git config --local kat.remote <url>` if it differs from the official HTTPS URL). For a release, bump `package.json`, commit the version change, and create a new annotated `vMAJOR.MINOR.PATCH` tag for that commit. Run `node kat.mjs sync v1.1.0` to review the target, current commit and tag. Once approved, run `node kat.mjs sync v1.1.0 --approve <commit>`. The CLI validates first and uses an atomic, non-force Git push. Stable tags serve as installer releases. A GitHub Release page can be added separately if you want release notes or a downloadable bootstrap asset; its metadata is optional for the installer. Never repoint a published release tag.

To check a new release on another machine run `node kat.mjs update`. Review the printed release hash, stop Studio and pass that hash to `update --approve`. Updates refuse a dirty checkout, a non-fast-forward history or a changed installed tag. Updates keep a Git branch at the previous commit. The installed skill lives outside the source checkout. If a future release changes the skill instructions, review the changes and reinstall the skill manually so existing local skill edits remain safe.

## Recover

Run `node kat.mjs save` before a release that changes the schema. Automated snapshots run while Studio is open. The verified snapshots include the database, private media referenced by its records, and the app files available to the backup. Restore into a new directory. Do not point an older app at a database already migrated by a newer release. For rollback, create a separate worktree from the reported `kat-backup/<commit>` branch and use the pre-update restored database with a separate port.

Logs are in `studio.log` in the install root. They can contain the private localhost URL. If an installation stops partway through, rerun the bootstrap. If `.install-lock` remains after a hard interruption, check for any running installer before removing the empty lock directory.
